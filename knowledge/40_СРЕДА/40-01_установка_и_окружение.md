# Установка и окружение

## Что нужно

| Что | Где берётся | Как находит mcukit |
|---|---|---|
| SEGGER J-Link Software | segger.com, пакет «J-Link Software and Documentation» | `MCUKIT_JLINK` → свежая `Program Files\SEGGER\JLink*` |
| arm-none-eabi-gcc | Arm GNU Toolchain или внутри STM32CubeIDE | `MCUKIT_GCC` → PATH → Arm GNU Toolchain → `C:\ST\STM32CubeIDE_*\...\gnu-tools-for-stm32*\tools\bin` |
| make | PATH или внутри STM32CubeIDE | `MCUKIT_MAKE` → PATH → `...\externaltools.make*\tools\bin\make.exe` |
| Python 3.11+ | python.org | — |

Рабочие папки заданий: `MCUKIT_WORK`, иначе `%LOCALAPPDATA%\Temp\mcukit`.
Там лежат файлы команд, журналы J-Link (`jlink.log`) и копии проектов —
первое место, куда смотреть при сбое.

Проверка:

```python
import mcukit as mk
mk.jlink_version(), mk.gcc_version(), mk.make_exe()
mk.probe()                 # зонд, VTref — к чипу не подключается
```

## Зонд с именем SAM-ICE

`ShowEmuList` показывает `ProductName: SAM-ICE`, железо J-Link V9.50,
лицензии `RDI,FlashBP,FlashDL,JFlash,GDB`. Официально SAM-ICE — вариант
J-Link для чипов Atmel/Microchip. Этот экземпляр подключился к GD32F470,
записал и прочитал флеш без ограничений. Другой экземпляр SAM-ICE может
вести себя иначе — проверять.

## Установка набора

`tools/setup.ps1` (или двойной щелчок по `Install-skill.bat`): junction
скилла, `MCUKIT_HOME`, хук коммитов, локальный стоп-лист, проверка
программ. Прав администратора не требует.

## Подключение агентов

Набор подключают к нескольким агентам одновременно. Все они читают **один и тот
же git-репозиторий**, а не копии:

```
MCU-Kit\                           ← git-репозиторий, единственный источник
   ├── skill\SKILL.md
   ├── knowledge\  tools\  mcukit\
   ↑
   ├── ~\.claude\skills\mcu               junction   (Claude Code)
   ├── ~\.kimi-code\skills\mcu             junction   (Kimi Code)
   └── ~\.config\opencode\skills\mcu       junction   (opencode)
```

Правка файла видна всем трём агентам мгновенно — это один и тот же файл, а не
синхронизация копий. На другую **машину** правка попадает только через
`git push` отсюда и `git pull` там.

**Цель junction — `<корень>\skill`, а не корень репозитория.** В opencode
`SKILL.md` обязан лежать прямо в каталоге скила, поэтому junction на корень
скилл не найдёт, а junction на корень репозитория протащит в агента всё
вместе с `.git`. База `knowledge\`, `tools\` и библиотека `mcukit\` лежат
уровнем выше; скрипты проектов находят их через `MCUKIT_HOME`, а не через
каталог скила.

`tools/setup.ps1` создаёт junction'ы к Claude Code и Kimi Code. Для opencode
junction создаётся отдельно:

```powershell
cmd /c mklink /J "$env:USERPROFILE\.config\opencode\skills\mcu" `
    "<корень набора>\skill"
```

Прав администратора не требуется — junction (`mklink /J`) создаётся без них,
в отличие от символической ссылки.

**Копия набора в каталоге агента — не то же самое, что junction.** В копии
правка, сделанная одним агентом, не появится у другого, и расхождение
обнаружится через месяцы, когда исходный агент уже не работает с этим набором.

### Симлинки и hardlink

Без прав администратора и без Developer Mode символические ссылки на файлы не
создаются (`New-Item -ItemType SymbolicLink` отклоняется). Работают только:

* **junction** (`mklink /J`) — для папок;
* **hardlink** (`mklink /H`) — для файлов.

Отсюда проверка через junction выглядит иначе, чем для обычной папки.
**PowerShell 5.1 не заходит в junction при `Get-ChildItem -Recurse`** — нужен
`-FollowSymlink`, а он появился только в PowerShell 6+. Пустой вывод
`Get-ChildItem` по junction не означает, что junction сломан; проверять
надо точечно:

```powershell
Test-Path "$env:USERPROFILE\.config\opencode\skills\mcu\SKILL.md"
```

`tools/check_docs.py`, `Read` и `Glob` по путям внутри junction работают
нормально — ограничение относится только к рекурсивному перебору в
PowerShell 5.1.

### Требования opencode к SKILL.md

`skill/SKILL.md` — единственный файл набора, к которому opencode
предъявляет строгие требования:

| Поле | Требование |
|---|---|
| `name` | 1–64 символа, строчная латинская с одиночными дефисами, **совпадает с именем каталога скилла** (`mcu`) |
| `description` | 1–1024 символа |
| прочие поля | `license`, `compatibility`, `metadata`; неизвестные игнорируются |

**Описание обернуть в кавычки, если в нём есть `: ` — двоеточие с пробелом.**
Это единственная причина, по которой YAML-парсер рвёт значение: двоеточие с
пробелом внутри некавыченного скаляра читается как переход к отображению.
Проверено на трёх скиллах набора: `solidworks` и `mcu` кавычек не имеют и
разбираются без ошибки, у `allegro` двоеточие с пробелом есть — и без кавычек
скилл не грузился.

Ошибка молчаливая: парсер не ругается, значение просто теряется, и в списке
скиллов агента набора нет — без всякого сообщения. Голый `;` YAML переваривает
без кавычек (проверено на всех трёх описаниях), но кавычки безвредны и
страхуют от `;` и `#` в будущих правках.

У лимита 1024 символа у `mcu` остаётся 821 символ занятости — формулировку
править осторожно: молча обрезанное описание хуже, чем короткое.
